SCAN 1(a) — RLS / write-permission audit · VERDICT: CLEAN

No entity currently denies a legitimate write. Enumerated all 134 entities (parsed, comment-stripped).
  • 22 entities carry the write-lock, now role:"admin" on create/update/delete — asServiceRole (admin-level) satisfies it; direct clients (role:"user") are blocked (the intended B3 protection). Zero role:"system" remain (that was the app-wide bug — it denied the service too).
  • 112 entities have no RLS block → platform default → authenticated owner writes + service writes both succeed (JournalEntries, DailyCheckins, PlannerItems, MealLog, SealedLetters, UserProfile, …).

Confirmed no client code reads any of those 9 directly (the only reference is documentation text in a FoundersOS doc) — all their reads go through service functions, so the lock doesn't break a client read.
Residual to watch (LOW): the 112 default entities permit a signed-in client to write its own rows directly — fine for personal data, but if any should be service-only that's a separate hardening pass (not a write-failure).

SCAN 1(b) — function hang audit · VERDICT: SYSTEMIC RISK

B1 — Unguarded awaited calls in interactive functions HIGH CLEAR-FIX (batched)

49 of 59 client-invoked functions have an awaited platform/entity call (get/filter/create/update/delete) or external fetch/InvokeLLM that is NOT timeout-guarded. This is the exact posting class: a plain .catch() only catches a throw — a call that hangs never settles, wedging the whole function (the user sees an endless spinner). Only the 5 community write fns + jessSupport were guarded before this audit.

Fix pattern (proven on posting): wrap every awaited platform/external call in withTimeout(p, ms) (race against a timer) — reads fail-open (skip + proceed), writes return a clean 500. Guards are the universal protection: they hold regardless of index state or model latency.

B2 — App-wide unindexed sorts HIGH NEEDS-HALLI (prioritize)

~100 sorted reads across the app sort on a field with NO index. An unindexed sort is what tipped the posting rate-cap read into a 27s+ hang. Only the 10 community entities indexed in 661e338 are covered; everything else sorts unindexed — e.g. DailyCheckins by date ×14, LifestyleItems by published_at ×15, UserProfile by created_date ×9 / date ×9, JournalEntries, MealLog, HabitLogs, Programs, UserPrograms, MedicationLogs, SymptomLogs, CycleEvents, ContentItems…

Judgment call (why not auto-add 100 indexes): the app runs daily on these reads, so unindexed sorts degrade/crawl but don't universally hang — the posting hang needed a large table + the RLS-denial interaction to tip over. So:
  • Primary fix = the B1 guards (universal, already in motion) — no read can wedge a function regardless of index.
  • Indexes = targeted optimization where live latency shows slowness. Recommend a prioritized add (highest-traffic + largest tables first): DailyCheckins.date, JournalEntries.created_date/session_date, MealLog, UserProfile, HabitLogs.date, LifestyleItems.published_at, Programs, UserPrograms. Halli decides scope (each is an additive, low-risk schema change like the community ones; cost is the entity sync + your call on which tables are big enough to matter).
