Calendar Sync
— Google & Apple

How FemWell's Planner and Logger could sync two-way with a user's Google and Apple calendars — so a rota you photographed, a planned meal, or a scan appointment shows up in their phone calendar, and their real-life events show up in FemWell. This is a plan. Building it crosses two hard lines (a new backend function + external OAuth credentials), so it's gated on your sign-off.

⛔ Build gate — read first This cannot be built inside our current rules. It requires all three: (1) a NEW base44 function (OAuth callback + sync worker — the photo work reused an existing function; this genuinely can't), (2) external OAuth credentials (a Google Cloud project + OAuth consent screen; an Apple app-specific-password or CalDAV setup), and (3) possibly paid quota / verification (Google API quota is free at our scale, but the OAuth consent screen needs Google verification because Calendar is a "sensitive/restricted" scope — a review process, not a bill). None of this should start without your explicit go-ahead. The rest of this doc is the plan for when you say yes.

1 · Current state — what exists today

I searched the whole codebase. There is no calendar sync, import, or export of any kind. Specifically:

An events sync functionrefreshEvents exists but it's community-event discovery (LLM-curated women's networking/fitness listings into an admin-only EventsItems table) — not a personal calendar sync.
Any OAuth integration to copyOnly Stripe (payments) — and that's an API-key, not an OAuth user-consent flow. So there's no OAuth pattern in the app to reuse — we'd build the first one.

The Planner data (PlannerItems) stores date (local YYYY-MM-DD), time (local HH:MM), title, category, and a repeat field (once/daily/weekly/monthly). Logs (MealLog, SymptomLogs, HabitLogs) key off a local day_key. Crucially: no timezone field, and no place to store an external calendar's event id — both of which sync needs.

2 · What "sync" should mean for FemWell

Two surfaces, two directions:

SurfaceOut → their calendarIn → FemWell
Planner (events, plans, the rota shifts we now parse)A planned shift / appointment / event appears in Google/Apple Calendar with time + location.Their real calendar events appear in the Planner day-view so FemWell knows when they're busy (and can plan cycle-aware around it).
Logger (retrospective logs — meals, symptoms, meds)Optional: a lightweight "took meds 8am" or "migraine 2pm" as a calendar event, for people who live in their calendar.Rarely inbound. Logs are FemWell-native; we don't pull food/symptoms from a calendar. So the Logger is export-mostly, one-way.
FramingThe Planner is the two-way surface (events flow both ways). The Logger is export-only and optional (and privacy-sensitive — a "migraine" or a fertility appointment in a shared Google calendar is a real disclosure risk, see §8). Lead with the Planner.

3 · Google Calendar — the approach

The mature, well-documented path. OAuth 2.0 + the Google Calendar REST API.

How it works

  1. Consent: user taps "Connect Google Calendar" in Settings → we redirect to Google's OAuth consent screen (scope calendar.events) → Google redirects back to our callback with an auth code.
  2. Token exchange: a base44 function swaps the code for an access token + refresh token, stored per-user (encrypted, server-side — never in the client).
  3. Export (out): when a Planner item is created/edited, the function calls events.insert/events.patch and stores the returned Google eventId on our row.
  4. Import (in): a sync worker calls events.list with a sync token (Google's incremental-sync mechanism — only changed events since last pull) and upserts them into the Planner.
Sync trigger options: on app open a "Refresh" button a daily cron push via Google "watch" webhooks (advanced) — recommend on-open + manual refresh for v1; webhooks later.

Cost/quota reality: the Calendar API is free at our scale (generous per-user quotas). The real cost is the OAuth consent-screen verification: calendar.events is a Google "sensitive scope," so the consent screen must pass Google review before >100 users can connect (a form + a demo video + a privacy-policy URL — days-to-weeks, not money). Until verified, it works for a test-user allowlist.

4 · Apple / iCloud — the harder one

Apple has no clean public Calendar REST API like Google. Three routes, none as tidy:

FiddlyA · CalDAV to iCloud

+ True two-way. – Requires the user to generate an app-specific password in their Apple ID (clunky UX), and CalDAV is a verbose XML protocol; iCloud's CalDAV is under-documented and quirky.

Best for v1B · .ics subscribe + export

+ Export FemWell → a hosted webcal:// feed the user subscribes to in Apple Calendar (read-only, auto-refreshing). Import their events → let them export an .ics from Apple Calendar and upload it (one-off). No passwords, no Apple API. – Not live two-way — the subscribe feed is one-way (FemWell → Apple), and inbound is a manual file, not continuous.

Native-onlyC · EventKit (a real iOS app)

– The proper native API — but needs a real iOS app wrapper. FemWell is a web app on femwells.com, so this is off the table until/unless there's a native shell.

Apple recommendationShip B (a webcal subscribe feed out + .ics upload in) for Apple users — no app-specific passwords, works today on a web app. Offer CalDAV (A) later only if users ask for live two-way. This means Apple is one-way-live + manual-in, while Google is fully two-way — set that expectation.

6 · How items flow (Planner + Logger)

Planner item created in FemWell → sync worker builds a calendar event (title, start = date+time in the user's tz, end = +duration or the parsed shift end, location, a "via FemWell" note) → events.insert → store the returned eventId + calendarId on our row so future edits patch the same event (no duplicates).
External event changes in Google → incremental events.list → for each: if it carries our marker it's ours (skip/update); else it's a real-life event we upsert into the Planner as a read-only "from your calendar" block, so cycle-aware planning routes around it.
The rota we now parse from a photo → the reviewed shifts (already PLAN entries, with overnight + location) → each becomes a Google event; a fixed weekly rota maps neatly to a Google RRULE recurring event (one recurring event instead of N copies — see §8).

Logger: meals/symptoms/meds are FemWell-native. Export is opt-in per type ("also add meds to my calendar as reminders"). Nothing about the cycle or symptoms goes to an external calendar unless the user explicitly turns that type on — default OFF.

7 · Data-model changes we'd need

Sync needs a few new fields (a schema delta — owned by Ms Data, done as an MP, backward-compatible/additive):

  • On PlannerItems: external_event_id, external_calendar_id, source (enum: manual | google | apple), synced_at (ISO), tz (IANA, e.g. Europe/London). These let us dedupe, patch the right event, and show "from your calendar."
  • A new CalendarConnection entity: user_id, provider, access/refresh token (encrypted), scope, sync_token, calendar_id, last_synced_at, status, revoked_at. One row per connected calendar.
  • On UserProfile: a timezone (IANA) — asked once at connect, or inferred from the browser (Intl.DateTimeFormat().resolvedOptions().timeZone). Today the app assumes local time everywhere with no tz stored; sync makes an explicit tz mandatory.

8 · Edge cases

CaseHandling
Duplicates (sync loops — our export comes back on import)Tag every FemWell-created event with an extended property / marker (femwell:itemId). On import, skip events carrying our marker (they're already ours). Store the external_event_id so re-exports patch, never re-insert.
TimezonesStore a real IANA tz per user; convert our local date+time → an RFC5339 datetime with tz for Google; convert incoming events back to local day_key+HH:MM. This is the single biggest correctness risk — the app currently has no tz at all.
Overnight shifts (3pm–12am, the rota case)We already flag end_next_day. In a calendar event, end = next day 00:00 in the same tz — a normal cross-midnight event. No all-day flattening.
Recurrence / fixed rotasA fixed weekly schedule → a single Google event with an RRULE (FREQ=WEEKLY), not 12 copies — cleaner and editable in one place. A flexible schedule → discrete events. (Maps directly onto the fixed/flexible model we just built into the Planner.)
Conflict (edited both places)v1 rule: last-write-wins by updated_at, and never delete a user's external event on our sync — only ones we created. Surface conflicts rather than silently overwriting.
Revoke / disconnect"Disconnect calendar" → revoke the token, stop syncing, and offer to remove the events we added (don't touch anything else). Mark imported blocks stale rather than deleting the user's data.
Privacy (UK GDPR)Health data leaving to a third-party calendar is a real disclosure. Logger export is opt-in per type, default OFF; a clear "this will appear in your Google/Apple calendar, which may sync to other devices/people" consent line; the privacy policy must name Google/Apple as processors.

9 · Exactly what building it requires

The three gates (all needed)
  1. A NEW base44 function (at least one): an OAuth callback handler + a sync worker (token refresh, events.list/insert/patch, dedupe). The photo feature reused analyzeMealPhoto; this genuinely cannot reuse an existing function — it's new backend surface. (Per the function-cap rule, this needs your OK.)
  2. External OAuth credentials: a Google Cloud project with an OAuth client ID/secret + a configured consent screen (privacy-policy URL, scopes, and — for >100 users — Google's verification review). For Apple: a hosting endpoint for the webcal feed (no creds) or, for CalDAV, the user's app-specific password.
  3. Secrets + schema: store GOOGLE_OAUTH_CLIENT_ID/SECRET via base44 secrets; add the CalendarConnection entity + the PlannerItems/UserProfile fields (§7) as an MP.

What's already in our favour: base44's serverless-function + env-secret pattern is proven (OpenAI/Stripe use it), the Planner has a repeat field, and we just built the fixed/flexible + overnight + location model that maps cleanly onto calendar events. So the app-side is largely ready; the new work is the OAuth function + Google project + the schema delta.

Rough effort (for scoping only, post-sign-off): Phase 1 (Google export-only) ≈ one focused build + a Google project setup; Phase 2 (import + dedupe + tz) is the bulk of the real engineering; Apple webcal/.ics ≈ a small add. Google verification is calendar-time (their review), not our build time.

10 · Recommended path + phasing

Recommendation Start with Google, export-only, from the Planner — it's the highest-value, lowest-risk slice (planned shifts/appointments land in the user's real calendar, no merge conflicts, no inbound tz headaches). Add Google import next (the two-way value). Do Apple via a webcal subscribe feed + .ics upload third (no Apple creds needed). Keep the Logger export opt-in and default-off for privacy. Treat each phase as its own sign-off.
Phase 1 · Google export

Connect Google (OAuth) → planned Planner items + reviewed rota shifts push out as events (fixed rotas as RRULE). Schema: CalendarConnection + the new PlannerItems fields + user tz.

Phase 2 · Google import (two-way)

Incremental events.list pulls real-life events into the Planner as read-only blocks; dedupe via markers; full timezone correctness. Cycle-aware planning now routes around real commitments.

Phase 3 · Apple

webcal:// subscribe feed out + .ics upload in. No Apple credentials. CalDAV only if users demand live two-way.

Phase 4 · Logger export + polish

Opt-in per type (meds/appointments), conflict-resolution UX, optional Google push webhooks.
