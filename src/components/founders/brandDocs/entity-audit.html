Part A — Removal

The mechanism · important

How base44 entity removal actually works

I traced the build/deploy path. The base44/entities/*.jsonc files are a local MIRROR, not the deploy source. The build is pure Vite over src/; nothing in scripts/deploy.mjs or the build reads the entities folder. deploy.mjs only POSTs the app bundle to /api/apps/<id>/deploy.

  • Deleting a .jsonc file + deploying does NOT remove the entity or its data from Base44 — it just desyncs the mirror. So there's no "remove via code" path.
  • Real removal is a Base44 platform action — the dashboard (app.base44.com → your app → Data → the entity → delete), which drops the table and all its rows (destructive, irreversible). The schema API exposed here has create/update but no delete, so it's a dashboard job.
  • Therefore code can't do this deletion — it needs you (or an authorised session) in the Base44 dashboard.

Part B — Consolidation

Read-only plan. Merges need data migration, so nothing here is built — this is the map + the order to do it in. Net entity reduction shown per merge.

Tier 1 · easy wins

Near-duplicate pairs · −8 entities

Two tables that are the same thing from different eras. Thin migrations, low risk. Do these first.

DrinkLog → HydrationLog−1

Why: DrinkLog = caffeine/alcohol + calories; HydrationLog = water volume. Near-identical schema (both user_id+day_key+amount_ml+drink_type).

Migration: Add `calories` to HydrationLog; migrate DrinkLog rows with their drink_type. Update ~7 DrinkLog call-sites.

KickLog → PregnancyKickSession−1

Why: Both are fetal-kick counting sessions. KickLog is the older shape (kick_count/duration_minutes) vs PregnancyKickSession (kicks/duration_seconds).

Migration: Map KickLog fields → PregnancyKickSession units; migrate ~2 call-sites; retire KickLog.

CommunityPosts + Posts → CommunityPost−2

Why: Three eras of the same thing: current anon rooms (CommunityPost) + MP#8 (CommunityPosts) + the original generic Posts.

Migration: Already flagged. Retire orphan CommunityMP8 page + legacy CommunityHub page first, then drop both old entities.

SupplementLog → MedicationLogs−1

Why: SupplementLog's wide boolean columns (folic_acid/vitamin_d/omega3/iron) are a legacy shape. A supplement is a med with category='supplement'.

Migration: Represent each supplement as a MedicationLogs row (item_name + category); migrate ~8 call-sites.

ContentBookmarks → SavedItems−1

Why: SavedItems is the general saver (item_type/item_id/title). A bookmark is just item_type='content'.

Migration: Migrate ContentBookmarks → SavedItems rows; update ~3 call-sites (some already read SavedItems).

HotFlashLog → MenopauseSymptomEntry−1

Why: A hot flash is one menopause symptom_type. MenopauseSymptomEntry already has symptom_type + severity + trigger_tags.

Migration: Migrate HotFlashLog rows as symptom_type='hot_flash'; update 1 call-site.

HairRoutine + SkinRoutine → BeautyRoutine (new, or fold to LogAction)−1

Why: Two thin one-off beauty logs (1 call-site each). Both are 'a beauty/self-care routine event'.

Migration: Either one BeautyRoutine entity with a `kind` (hair/skin) field, or fold into a generic tracking log. Small.

Tier 2 · type-discriminator merges

Fold variants into one typed table · −16 entities

Several tables that are really one shape with a type/action field. More call-sites to migrate, but big structural payoff (esp. the content-interaction merge).

ContentHistory + ContentRatings + PodcastListens + ReadingActivity → ContentInteraction (base = LifestyleInteractions)−4

Why: All are 'user did X to a content/lifestyle item' events. LifestyleInteractions already has action+category+item_id. ContentHistory=completion, ContentRatings=stars/review, PodcastListens=position, ReadingActivity=progress.

Migration: Unify to one interaction table: action ∈ {view,complete,rate,listen,read,progress} + a meta_json carrying stars/position/completion. This is the single biggest structural win but touches the whole content/lifestyle read layer.

AdviceThreads + AdviceMessages + AdviceHistory → JessConversation / JessMemory−3

Why: Advice threads/messages mirror a chat — the same shape as Jess. Three Advice* entities duplicate the assistant-conversation model.

Migration: Fold Advice threads/messages into JessConversation (role/content/thread) + JessMemory; retire the 3 Advice* entities. Check the advice UI + the 1 backend fn.

InvisibleTask + LifeAdminItem → PersonalTasks−2

Why: Three task-ish entities. InvisibleTask (mental-load carry/hand-off) + LifeAdminItem (admin due/disposition) are variants of PersonalTasks (title/date/category/completed).

Migration: Add category/meta to PersonalTasks to carry the invisible-load + life-admin fields; migrate ~2 call-sites each.

StoryPack + StoryVisualPool → StoryItem−2

Why: Backend story-generation pipeline split across StoryItem + StoryPack + StoryVisualPool (+ DailyStory as the surfaced one).

Migration: Collapse the generation-side pack/visual-pool into StoryItem with a status/type; keep DailyStory as the read surface. Backend-only, so no UI churn.

DealsItems → Deals−1

Why: Deals + DealsItems (+ the two killed DealsProducts/DealsSources). One deal object with a type is enough.

Migration: Fold DealsItems (coupon-shaped) into Deals with a `kind`; migrate the 2 backend fns.

ProgramRecommendations → Recommendations (unified)−1

Why: TodayRecommendations + ProgramRecommendations are the same 'a recommendation for a surface' shape.

Migration: Add a `surface` field to TodayRecommendations and fold ProgramRecommendations in.

NutritionInsight → InsightCards−1

Why: InsightCards already has a `type` enum (PHASE/SKIN/NUTRITION/SLEEP/MOOD...). NutritionInsight duplicates the nutrition slice.

Migration: Emit nutrition insights as InsightCards type='NUTRITION'; migrate ~12 nutrition call-sites (bigger read surface).

PainMap → SymptomLogs−1

Why: PainMap = a symptom with a body `region`. SymptomLogs is the general daily symptom log.

Migration: Add `region`/`pain_type` meta to SymptomLogs; migrate PainMap's ~3 call-sites.

BbtLog + OpkLog → FertilityLog (new)−1

Why: BbtLog (basal temp) + OpkLog (ovulation test) are both single-metric fertility trackers used together.

Migration: One FertilityLog with metric ∈ {bbt,opk} + value/result; migrate ~4+4 call-sites.

Tier 3 · bigger migrations

Structural · −3+ entities · do last

Highest payoff-per-table but touches wide read layers. Plan carefully; not a first move.

MenopauseProfile + PregnancyProfile + NutritionProfile + LifestyleProfile → UserProfile (nested) or Profile{domain,data}−3

Why: Five+ single-row per-user 'profile' entities. Each is one row per user holding a domain's settings. UserProfile is already 60 fields.

Migration: Either nest these as JSON sections on UserProfile, or a generic Profile{domain,data_json}. Touches many read sites across the app — highest migration cost, do last.

(evaluate) DailyPromptResponse, Intention, SkyNote, others → TrackingLog (polymorphic daily log)−0

Why: ~47 entities are user_id+date+a few fields. A fully polymorphic daily log (type+payload) could absorb many single-domain logs — but risks over-normalising and losing typed queryability.

Migration: NOT recommended wholesale. Only unify logs that share query patterns. Listed as the aggressive ceiling, not a first move.

How to confirm what's really waste

Signals + where to get them

  • Row count = 0 → dead, delete. Where: Base44 dashboard → Data (per-entity count), or the data connector.
  • Last-write date old / never → abandoned even if it once held rows. Where: query -updated_at limit 1 per entity via the data connector.
  • Backend-only + owning function dead → the 12 backend-only entities (Fiction*, Story*, Voice*, WeeklyBookPick…) are only safe to keep if their pipeline still runs. Where: check the function's last invocation / whether it's still scheduled.
  • Few call-sites + thin schema → merge candidate (already mapped above). Where: this audit's ref counts.

The one thing I'm missing is the live DB. Everything else (refs, schemas, overlap) is done. Give me the data connector or read the counts off the dashboard and the picture is complete.
