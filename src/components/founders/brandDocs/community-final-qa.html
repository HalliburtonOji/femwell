The one P0 — DM identity is a bearer token (open)

What's solid: Conversation & Message are fully admin-RLS-locked (no client can query them). Every dm.* op runs asServiceRole, checks the caller is a participant, and screens every message before delivery (crisis floor → banned-word → OpenAI); held messages reach nobody; dm.messages reads delivered-only. That part is genuinely well-built.

The gap: the dispatcher trusts the client-supplied author_hash as the caller's identity (createCommunityPost/entry.ts:177,193) — it can't recompute it (the hash = sha256(community::userId::deviceSecret) and the device secret never leaves the phone). That same hash is publicly harvestable: it ships on every public CommunityPost row (used for presence/alias/"ask to chat"), and on BuddyRead/EventPod rows and the DM other_hash.

The exploit: a signed-in user (via the SDK / devtools, not the UI) reads a stranger's author_hash from a public post, then calls createCommunityPost {action:"dm.conversations", author_hash:<hers>} (user_id is optional, so the me.id guard is skipped) → gets her conversation list; then dm.messages → reads her delivered message bodies; and could dm.send/dm.block as her. The admin-lock is bypassed because the trusted function does the read on the forged identity's behalf.

Why not blind-fixed: the correct fix is an identity re-architecture — never expose a raw author_hash to clients; do all hash-targeting server-side by post/comment id (e.g. "ask to chat" sends a post_id; the server resolves the author hash), and derive/verify DM identity server-side. That changes how presence, alias, hide-a-voice and "ask to chat" get their token and needs a small migration. Shipping it unreviewed in a QA pass risks locking women out of their own threads (per-device secrets mean one woman legitimately has several hashes). This is your call.

Severity note: exploiting it needs technical effort (an SDK/console call), not a tap — but for a women's-safety app whose stated guarantee is "a client can't query someone else's chat," it's a real gap between promise and implementation. Recommend prioritising the server-mediated-targeting refactor next.

Fixed & deploying this pass

fixed Comment-level safety parity (Community.jsx). The device-local hide-a-voice and mute-a-word filters were applied to posts only — a muted word or a hidden voice still showed in replies (a pile-on vector). Now applied to comments/replies too (never hides Jess or your own line).

fixed Report a comment. There was no way to report an abusive reply — only posts — even though the server already supports report with target_type:"comment" (auto-hides at threshold). Added a Report (and Hide) control to every member comment.

fixed Cross-user shelf bleed (bookshelf.js). The Library shelf's local mirror used one global key (fw_bookshelf), so on a shared device / account switch, one woman's shelf showed to the next user and migrated up into her UserBook. The mirror is now scoped per user_id; server UserBook rows remain the source of truth.

Flagged — needs you (not blind-fixed)

flag Broadcast free-text notes aren't server-screened or reportable (P1). EventPod "go-together" notes and BuddyRead buddy notes are written straight to the entity with only a client-side crisis check — they skip the publish-then-screen (OpenAI) pipeline the rooms use, and there's no report/hide control in their sheets. They're short, in-app, pseudonymous and admin-hideable, but they're text broadcast to other women (some meeting in person). Recommend: route both through a screened dispatcher action + add an inline report affordance (small function work — flagged, not built, to respect the 50-fn cap intentionally).

flag The "no post left unanswered" Jess reply is client-triggered, not guaranteed (P1). The backstop jessSupport call fires only when a thread is opened (Community.jsx). A quiet post whose author never re-opens it can sit with zero replies. A server-side sweep would make the guarantee real (needs a notify/cron path — already on the parked list).
