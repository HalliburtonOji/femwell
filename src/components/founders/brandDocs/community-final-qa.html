The P0 — DM identity spoofing — FIXED & LIVE

The gap (was): the dm.*/game.* dispatcher trusted the client-supplied author_hash as the caller's identity — and that hash is publicly harvestable (it ships on public post rows). A signed-in user could spoof a stranger's hash and call dm.conversations/dm.messages to read her private conversation list + delivered message bodies (or dm.send/dm.block as her). The admin-RLS lock was bypassed because the trusted asServiceRole function did the read on the forged identity's behalf.

The new identity model (deployed): identity is now proven server-side, never asserted by the body.

  • The community author_hash = sha256("community::"+userId+"::"+deviceSecret). The client now sends the device secret with every dm.*/game.* call; the server recomputes the hash from the authenticated me.id + that secret and rejects (403) unless it matches the presented author_hash (verifyIdentity, constant-time compare).
  • A forged/harvested hash gets you nothing: to pass, you'd need a secret that hashes, with your own authenticated id, to someone else's hash — preimage-resistant. Absent secret → 403. Admins bypass (moderation tooling) only.
  • DM targeting no longer harvests a hash: "ask to chat" now sends the target's post/comment id; the server resolves her identity + derives both aliases server-side (dm.request → target_post_id). target_hash kept only as a transitional fallback.

Existing threads preserved — no migration, no lock-outs (the key worry): identity is still the same device hash, so every existing Conversation/Message resolves exactly as before — same device → same secret → same proof → same threads. Nothing is rewritten. The per-device multi-hash reality is handled natively: each device has its own secret+hash and each verifies independently against me.id; a woman on two devices keeps whatever access she had before (unchanged). Account-switch on a shared device correctly yields a different verified identity (as it already did).

Verification (traced — criteria a/b/c): (a) dm.conversations/messages filter on the proven ah, so a caller only ever sees threads she's a participant in; (b) a forged/absent-secret body hash → 403, nothing returned; (c) the legit owner on her own device reproduces the same hash+secret → verifies → her existing threads open. Live checks: function deployed & healthy (loads, returns 401 on the pre-gate auth check, no 500 from the new crypto), and both hosts serve the matching client that sends device_secret.

Verification limit (honest): a live black-box test of the non-admin 403 wasn't possible from the QA environment — the only available account (founder) bypasses the gate by design, the CLI exec tool hit a local file-lock, and the browser wasn't driven (per instruction). Verification is therefore by rigorous code-trace + deploy/health/sync confirmation. Files: entry.ts (verifyIdentity gate + server-side alias + post-id resolution), communityAnon.js (communitySecret), dm.js/gamematch.js (send proof), Community.jsx (target by post id). Commit 364e4c4. Reversible: git revert.

Broadcast notes — screened & reportable — FIXED & LIVE

served.js — resolved (Part 3)

What it is: served.js is a git-tracked, minified build artifact (a full-app bundle — it opens with mangled JS + the React production licence) that some build sessions re-commit. The ~1,200-line uncommitted diff present at the start was stale minification churn from an earlier session's partial build (same logic, different mangled variable names). Running the build during this pass regenerated it back to match the committed HEAD, so it is now clean — nothing to commit or discard. It is not referenced by the deploy path (deploy.mjs/site deploy build from src/ + base44/functions/), so it's effectively vestigial. If it ever shows a stray diff again, git checkout -- served.js discards it safely.
